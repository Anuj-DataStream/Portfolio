01

Project thesis

A real problem became a complete system.

The idea

Do not automate one step. Improve the whole workflow.

The project began with a simple observation inside a college library: students were still recording their visits manually in a physical register. The goal was therefore not simply to replace handwriting with an RFID reader. The goal was to rethink the complete workflow around identification, entry, exit, record storage, occupancy, analytics, and access to information.

The resulting concept connects a physical identification point to a digital data system. A student's RFID card is read by an ESP32, the visit is processed as an entry or exit, the record is sent to Google Sheets through Google Apps Script, and the resulting data can drive analytics and a library dashboard.

Engineering principle

“If I notice a problem and decide it is worth solving, I will learn whatever is necessary to solve it—even if I start from zero.”

The mindset behind the project.

02

Observation → problem definition

The problem was visible before the technology was chosen.

What was observed

Every library visit starts with a manual transaction.

A student enters the library, writes their details in a register, and later records the exit. Over many visits, this produces a large collection of handwritten records that are difficult to search, process, and turn into useful information.

From the student's perspective, the process can create queues and unnecessary friction. There is also no simple way for a student to know the current occupancy of the library before making the trip.

Pain points

  1. Manual entry Students repeatedly write visit details in a physical register.
  2. Time and queues Writing and registration adds friction at the entrance.
  3. Difficult records Old handwritten records are harder to search and process.
  4. Limited visibility Students cannot easily check current library occupancy beforehand.
  5. Unused data potential Raw visit records can be valuable for analytics but are difficult to analyze manually.

Problem definition

How can a library replace repetitive manual entry with a faster, reliable, searchable and analyzable digital workflow while keeping the student experience simple?

Student requirements

  • Fast identification without handwriting.
  • Clear entry and exit confirmation.
  • Minimal waiting at the entrance.
  • Ability to view current occupancy information.

Staff requirements

  • Reliable identification and attendance records.
  • Simple student/RFID registration management.
  • Current students-inside information.
  • Access to daily operational records.

Administration requirements

  • Long-term records.
  • Analytics and reporting.
  • Configurable library capacity.
  • Historical data preservation.

03

System design decisions

Every major component exists for a reason.

Key design decisions made during the project
Decision Chosen approach Why it fits the problem
Identification RFID Fast, contactless, reusable, low-effort and suitable for repeated visits.
Controller ESP32 Combines embedded control with Wi-Fi connectivity in one compact platform.
Development environment VS Code + PlatformIO + Wokwi Enabled structured embedded development and digital hardware testing before physical deployment.
Data layer Google Apps Script + Google Sheets Provides an accessible cloud-backed record system without building a large backend from scratch.
Attendance model One complete row per visit Preserves the familiar register concept while making it digitally searchable and analyzable.
Entry/exit logic First valid scan = entry; second = exit Allows repeated library visits without overwriting previous visits.
Historical students Deactivate, do not delete Preserves historical attendance linked to the student's Student ID.
Rejected RFID Access denied without normal attendance record Unknown cards cannot enter the attendance workflow.

Identification & access

Know who is asking for access.

The RFID card provides the student's identity. The ESP32 reads the card and checks whether the RFID UID belongs to a registered student.

  • Registered card → continue
  • Unknown card → Access Denied
  • Entry → one buzzer beep
  • Exit → two buzzer beeps
  • LCD provides immediate feedback

Core workflow

From a card tap to a complete library record.

01

Student scans RFID

The RFID reader captures the card UID.

02

ESP32 identifies the student

The UID is matched against registered student information.

03

System determines the action

The next valid state is treated as Entry or Exit.

04

Device confirms the action

LCD displays the student's name and confirmation; buzzer provides an audio signal.

05

Data reaches the cloud layer

ESP32 communicates with Google Apps Script and Google Sheets.

06

Records become insights

Analytics and dashboard views use the updated attendance data.

Entry / exit state logic

First valid scan → Entry
Second valid scan → Exit
Next visit → Entry again

This allows multiple visits in a day. Each completed visit is preserved as its own row instead of overwriting an earlier visit.

08

Development journey

The build process is part of the project.

This section intentionally documents how the system was developed, not only what the final system looks like.

  1. 01

    Observe

    Notice the manual library workflow.

    The project started with a real-world observation rather than a technology-first idea: students and staff were still dependent on a physical entry/exit register.

  2. 02

    Define

    Expand the problem beyond attendance.

    The target became a complete workflow: identification, entry, exit, searchable records, occupancy, analytics, and a better student experience.

  3. 03

    Research

    Learn the technologies required by the solution.

    RFID, ESP32, PlatformIO, Wokwi, Google Apps Script, and the ESP32-to-Google-Sheets workflow were new areas of direct work. Existing Arduino and IoT experience reduced the learning curve.

  4. 04

    Experiment

    Build and break small pieces.

    Development involved brainstorming, online research, documentation, GitHub examples, ChatGPT, simulation, trial-and-error, and debugging error messages.

  5. 05

    Integrate

    Connect the previously separate pieces.

    The major breakthrough came from learning to use Wokwi with VS Code and PlatformIO and then successfully connecting the ESP32 workflow to Google Sheets.

  6. 06

    Debug

    Work through real system-level problems.

    RFID identification, ESP32/Wi-Fi communication, Apps Script, synchronization, entry/exit state logic, dashboard updating, and hardware constraints all required iteration.

  7. 07

    Validate

    Test the complete digital prototype.

    Multiple cards, repeated visits, multiple students, unknown cards, duplicate/wrong scans, different branches, sheet accuracy, dashboard updates, and ESP32 reconnection were tested in Wokwi.

  8. 08

    Build next

    Move from validated simulation to physical implementation.

    The next stage is the physical prototype, enclosure, and offline storage behavior, followed by real-world testing and refinement.

14

Reliability & edge cases

Designing for what happens when things go wrong.

Unknown RFID

Response: “Access Denied / Unknown Card” with a stronger alert. No normal attendance record is created.

Lost or damaged card

Response: Deactivate the old RFID UID and register a new UID against the same Student ID so history remains preserved.

Student leaves college

Response: Deactivate the student instead of deleting them. Historical records remain available.

Internet unavailable

Planned behavior: Store the scan locally, allow the transaction, warn about unsynced data, then synchronize when connectivity returns.

Capacity reached

Interpretation: “At Capacity” means the configured capacity has been reached; it does not guarantee that the physical library is actually full.

Multiple visits

Response: Entry → exit → entry again. Each completed visit becomes its own attendance row.

Future scope

Build Version 1 properly before expanding Version 2.

There are many possible directions, but the current priority is to make Version 1 reliable, physically validated, and useful before adding complexity.

Mobile access

Bring occupancy and system information into a mobile-friendly experience.

Notifications

Notify authorized users about relevant events or system conditions.

Better authentication

Add stronger role-based identity and access control.

Advanced analytics

Expand usage patterns, trends, reports, and decision-support metrics.

Multiple libraries

Scale the architecture beyond a single library or location.

Face recognition

Explore additional identity verification where appropriate and justified.

Cloud database

Move from spreadsheet-backed storage to a dedicated database as scale demands.

Admin login

Formalize role-based authentication and administration.

Automatic capacity calibration

Explore methods for making occupancy estimates more representative of physical conditions.

Current priority: physical prototype → offline storage → real-world testing → refinement.

What this project says about the builder

The technology was unfamiliar. The problem was not.

This project represents a way of working: identify a real problem, define what a useful solution should do, learn unfamiliar tools, build small pieces, connect them, debug failures, test the complete workflow, and keep improving it.

  • Identify real-world problems and build solutions.
  • Learn unfamiliar technologies quickly when the problem demands them.
  • Integrate hardware, software, and data into one system.
  • Troubleshoot and iterate independently.
  • Take an idea all the way toward a working prototype.
  • Do not let a lack of initial knowledge become the reason not to solve a problem.
